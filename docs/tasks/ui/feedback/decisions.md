### Dec-1. 좋아요/싫어요 투표 제거
영향도: significant · 출처: ai-suggested

문제 — 피드백 창에 좋아요/싫어요 투표가 필요한가?
옵션
  (A) 없애고 바로 입력
  (B) 남기되 둘 중 무엇을 골라도 입력창 열기
  (C) 입력창은 처음부터 보이고, 투표는 선택 사항
  (D) 지금처럼(싫어요일 때만 입력) 두고 1회 제한만 추가
선택 — A
근거 — 설정 메뉴에서 들어온 사람은 이미 무언가 쓰려는 사람이라 투표는 단계만 하나 늘린다. D는 즐겁게 플레이한 사람의 개선 제안을 받을 길이 없다. B·C는 만족도 신호를 남기지만, 결과창 기획(`result-box.md`)에서 이미 "좋았다/별로였다 투표 없이 의견은 피드백으로 받는다"고 정했고, 날짜와 상관없는 누적 만족도는 개선에 쓸 곳이 적다. 대신 `Survey Vote` 이벤트는 더 이상 쌓이지 않는다
영향 — classic·excel `SurveyForm`, Dec-8(이벤트), Dec-9(제목·문구)
상태 — active

### Dec-2. 1회 제한의 범위: 퀴즈 날짜(KST)당, 기기·브라우저 단위
영향도: significant · 출처: ai-suggested

문제 — "피드백 1회"를 어느 범위로 셀 것인가?
옵션
  (A) 퀴즈 날짜(KST)당 1회, localStorage에 저장
  (B) 영구 1회
  (C) 페이지가 열려 있는 동안 1회 (저장하지 않음)
선택 — A
근거 — 매일 문제가 바뀌는 게임이라 "오늘 퀴즈에 대한 의견 하나"가 자연스럽고, 도배도 하루 1건으로 막힌다. B로 하면 나중에 생긴 버그나 다른 날 문제에 대한 의견을 받을 수 없다. C는 새로고침하면 풀린다. 서버에서 막는 방식이 아니라서 다른 기기나 저장소 삭제로 우회할 수는 있지만, 목적은 실수로 여러 번 보내는 것과 가벼운 도배를 막는 것이라 이 정도로 충분하다
영향 — 공통 훅, Phase 2·3, Dec-5, Dec-10
상태 — active

### Dec-3. 보낸 뒤: 창 안에 감사 안내, 진입 버튼은 그대로
영향도: local · 출처: ai-suggested

문제 — 보낸 뒤나, 같은 날 피드백 창을 다시 열었을 때 무엇을 보여줄 것인가?
옵션
  (A) 입력창·버튼 자리에 감사 안내(내일 다시 남길 수 있다는 안내 포함). 진입 버튼은 그대로
  (B) 설정 메뉴·결과창의 진입 버튼을 비활성화
  (C) 감사 안내와 함께 보낸 본문을 읽기 전용으로 보여줌
선택 — A
근거 — B는 왜 막혔는지 설명할 자리가 없다. C는 본문을 localStorage에 남겨야 해서 공용 기기에서 개인정보 부담이 생긴다. 성공 alert도 이 안내로 대신한다
영향 — classic·excel `SurveyForm`
상태 — active (Dec-16으로 잠시 대체됐다가 Dec-18로 되돌림. 감사 안내의 내일 안내는 Dec-18에서 뺌)

### Dec-4. 전송 실패는 실패 토스트로, 1회로 세지 않음
영향도: local · 출처: ai-suggested

문제 — 웹훅 오류나 네트워크 끊김으로 보내지 못했을 때 어떻게 알릴 것인가?
옵션
  (A) 실패 토스트
  (B) 입력창 아래 경고 문구 (없는 단어 경고와 같은 방식)
  (C) 브라우저 alert 유지
선택 — A
근거 — 힌트·포기·링크 복사 실패와 같은 방식이 되고, 하네스 `h.failureToastShown()`으로 바로 검증할 수 있다. B는 모달 안에서 더 잘 보이지만 다른 실패와 방식이 갈린다. C는 디자인이 따로 놀아서 error-ui todo에서도 대체 대상이다. 토스트의 모바일 위치와 색 문제는 모든 실패 표시에 공통이므로 error-ui todo에서 함께 정리한다. 실패하면 입력을 그대로 두고 1회로 세지 않아 바로 다시 보낼 수 있다
영향 — 공통 훅, `docs/todo/error-ui.md` 표의 "피드백 제출 실패" 행(다른 작업 문서라 완료 시 보고)
상태 — active

### Dec-5. excel 테마도 동작만 같이 바꾸고 로직은 훅 하나로 공유
영향도: significant · 출처: ai-suggested

문제 — excel 테마 피드백 창(설정 메뉴에서만 열림)도 바꿀 것인가?
옵션
  (A) 동작은 같게 바꾸고(투표 제거, 1회 제한, 감사 안내, 실패 토스트) 셀 모양은 유지. 전송·저장 로직은 훅 하나로 묶어 두 테마가 공유
  (B) classic만 바꾸고 excel은 그대로
선택 — A
근거 — 두 폼이 같은 웹훅으로 보내므로, B로 하면 테마만 바꿔서 같은 날 다시 보낼 수 있어 1회 제한의 의미가 줄어든다. 지금까지 UI 작업은 "excel은 그대로"였지만, 이번 건은 모양이 아니라 규칙이라 예외로 둔다
영향 — `excel/SurveyForm.tsx`, Phase 3
상태 — active

### Dec-6. 여러 줄 입력, 최대 500자, 남은 글자 수 표시
영향도: local · 출처: ai-suggested

문제 — 하루 한 번만 보낼 수 있으니 한 번에 충분히 쓸 수 있어야 한다. 입력창을 어떻게 할 것인가?
옵션
  (A) textarea(4줄 정도) + 최대 500자 + 남은 글자 수 표시
  (B) textarea, 길이 제한 없음
  (C) 지금처럼 한 줄 input
선택 — A
근거 — 한 줄 input은 긴 글이 옆으로 밀려 보이지 않는다. 길이 제한이 없으면 웹훅으로 지나치게 큰 본문이 갈 수 있다. 공백만 있으면 보내기를 비활성화하는 것은 지금과 같다
영향 — classic·excel `SurveyForm`
상태 — active

### Dec-7. 웹훅 본문에 맥락 필드 추가 (식별자 없이)
영향도: significant · 출처: ai-suggested

문제 — 웹훅에 무엇을 함께 보낼 것인가? 지금은 `{ feedback, timestamp }`뿐이라 어느 퀴즈 얘기인지, 게임을 끝낸 사람인지 알 수 없다
옵션
  (A) 퀴즈 날짜, 테마, 진입점(설정/결과창), 그날 게임 상태(진행 중/맞힘/포기) 추가
  (B) 퀴즈 날짜만 추가
  (C) 지금처럼
선택 — A
근거 — "오늘 문제 너무 어려워요" 같은 의견은 날짜와 진행 상태를 함께 봐야 해석할 수 있다. 게스트 ID나 사용자 ID처럼 개인을 알아볼 수 있는 값은 넣지 않는다. Make.com 시나리오가 새 필드를 버리지 않는지는 확인해야 한다(plan Prerequisites)
영향 — 공통 훅, Dec-11
상태 — active

### Dec-8. Amplitude: 본문을 빼고 열림·보냄을 기록
영향도: local · 출처: ai-suggested

문제 — 피드백 관련 Amplitude 이벤트를 어떻게 할 것인가? 지금은 `Feedback Submitted`에 본문이 통째로 들어가 Amplitude(미국 리전)에도 쌓인다
옵션
  (A) `Feedback Opened`(진입점, 테마) 추가. `Feedback Submitted`는 본문 대신 글자 수·진입점·테마. `Survey Vote` 제거
  (B) `Submitted`에서 본문만 빼기
  (C) 그대로
선택 — A
근거 — 본문은 웹훅에 이미 있으니 Amplitude에 중복으로 둘 이유가 없다(privacy-terms todo의 검토 항목). 열어 본 사람 대비 보낸 비율을 보면 창 문구(Dec-9)가 효과가 있는지 판단할 수 있다

### Dec-9. 창 문구: 제목 + 안내 한 줄 + 예시 placeholder
영향도: local · 출처: user-suggested

문제 — 투표가 없어지면 "게임이 재미있었나요?"라는 제목이 맞지 않는다. "게임 개선에 도움이 된다"는 안내를 넣어 창 문구를 어떻게 구성할 것인가?
옵션
  (A) 창 제목 "피드백" 유지 + 안내 한 줄(무엇이든 적어 달라, 게임 개선에 도움이 된다, 하루 한 번) + 쓸 거리 예시를 담은 placeholder(불편한 점, 오늘 문제 난이도, 바라는 기능)
  (B) 제목 + "게임 개선에 도움이 돼요" 한 줄만. 하루 1회는 보낸 뒤에만 알림
선택 — A
근거 — "게임 개선에 도움이 된다"는 사용자 요구다(user-suggested). 구성은 AI가 제안해 사용자가 골랐다. 하루 한 번이라는 걸 미리 알려야 쓰다가 멈추거나 나눠 쓰지 않는다. 정확한 문구는 사용자가 코드에서 다듬는다. excel 테마는 셀 안의 같은 위치에 같은 정보를 담는다
영향 — classic·excel `SurveyForm`
상태 — superseded by Dec-15 (안내에서 하루 한 번 제외)

### Dec-10. 1회 판정 날짜는 보내는 시점의 KST 날짜

문제 — 23:59에 창을 열고 0:01에 보내면 어느 날짜로 기록하는가?
옵션
  (A) 보내는 시점의 `getKSTDateString()`
  (B) 창을 연 시점의 날짜
  (C) 화면에 걸린 게임 날짜(`useGameDate`)
선택 — A
근거 — 1회 제한은 "하루 한 번 보내기"를 막는 규칙이라 보낸 시각이 기준이 된다. C는 설정 메뉴(헤더)에서 게임 날짜에 접근하기 어렵다. 다시 열 때는 그 시점의 KST 날짜와 저장값을 비교한다
영향 — 공통 훅, Dec-2

### Dec-11. 설정 메뉴에서 연 경우 게임 상태는 localStorage 게임 기록에서 읽음
영향도: local · 출처: ai-selected

문제 — 설정 메뉴(헤더, 게임 컴포넌트 밖)에서 연 피드백 창은 그날 게임 상태(Dec-7)를 어디서 얻는가?
옵션
  (A) 보낼 때 localStorage `newmantle_game_data`에서 그날 기록을 읽어 진행 중/맞힘/포기를 정함
  (B) 게임 상태를 context로 올려 헤더에 전달
  (C) 설정 메뉴에서 보낼 때는 게임 상태를 빼고 결과창에서만 보냄

영향 — 공통 훅, Dec-7

### Dec-13. 엔터는 줄바꿈, 보내기는 버튼으로만
영향도: local · 출처: ai-selected

문제 — 여러 줄 입력창(Dec-6)에서 엔터를 누르면 무엇을 하나?
옵션
  (A) 줄바꿈. 보내기는 버튼으로만

### Dec-14. 저장 키와 게임 상태 값
영향도: local · 출처: ai-selected

문제 — 보낸 날짜를 어떤 키에 저장하고, 웹훅 `gameStatus` 값을 무엇으로 나눌 것인가?
옵션
  (A) 키 `newmantle_feedback_sent_date`(값은 KST `YYYY-MM-DD`). `gameStatus`는 `playing`(오늘 기록이 없거나 끝나지 않음) / `solved` / `given_up`
  (B) `gameStatus`에 `not_started`(오늘 입력 없음)를 따로 둠
선택 — A
근거 — 키 이름은 기존 `newmantle_*` 관례를 따른다. 피드백을 해석하는 데는 "끝냈는지"가 중요하고, 시작 전과 진행 중을 나눌 필요는 아직 없다. 필요해지면 B를 추가한다(기존 값은 바뀌지 않는다)
영향 — 공통 훅, verification F-2·F-3, Dec-7, Dec-11
상태 — active

### Dec-15. 안내 문구에 하루 한 번을 적지 않음
영향도: local · 출처: user-suggested

문제 — 피드백 창 안내 한 줄에 "하루에 한 번 보낼 수 있다"를 미리 적을 것인가?
옵션
  (A) 적는다 (Dec-9)
  (B) 적지 않는다. 안내는 무엇이든 적어 달라 + 게임 개선에 도움이 된다만

근거 — 화면 확인 중 사용자 요청: 굳이 명시하지 않아도 된다. 제한은 보낸 뒤 다시 열었을 때 감사 안내("내일 다시 남길 수 있어요")로 알 수 있다
영향 — classic·excel `SurveyForm` 안내 문구, Dec-9
상태 — active

### Dec-16. 보내면 피드백 창을 닫고 이전 창으로 돌아감, 성공 토스트로 알림
영향도: local · 출처: user-suggested

문제 — 보내기에 성공하면 어떤 화면을 보여줄 것인가?
옵션
  (A) 창 안에 감사 안내 (Dec-3)
  (B) 피드백 창을 닫고 연 곳으로 돌아감. 설정에서 열었으면 메인, 결과창에서 열었으면 결과창을 다시 연다. 성공은 토스트로 알림
선택 — B
근거 — 이전 창으로 돌아가는 것은 화면 확인 중 사용자가 요청했다. 창이 바로 닫히면 보냈다는 걸 알 곳이 없어서 성공 토스트를 더했다(이 부분은 ai-selected, 링크 복사 완료 토스트와 같은 방식). 보내지 않고 닫으면 지금처럼 이전 창으로 돌아가지 않는다(결과창 R-4-2). 같은 날 다시 열면 창 안 감사 안내는 그대로 보인다
영향 — `useFeedback`(보낸 뒤 콜백), `FeedbackDialog`·`NewMantleForm`(결과창 다시 열기), `SettingsButton`(설정 피드백 창 닫기), Dec-3
상태 — superseded by Dec-18 (요청을 잘못 해석함)

### Dec-17. 입력창 글씨: PC는 작게, 모바일은 16px
영향도: local · 출처: ai-selected

문제 — 입력창과 placeholder 글씨가 너무 크다는 요청. 얼마나 줄일 것인가?
옵션
  (A) 모든 화면에서 14px(`text-sm`)
  (B) 모바일 16px(`text-base`) 유지, `sm` 이상(PC)은 14px
선택 — B
근거 — iOS Safari는 글씨가 16px보다 작은 입력창에 포커스하면 화면을 확대한다. A를 쓰면 모바일에서 입력할 때마다 화면이 확대돼 결과창·피드백 창이 어긋난다. 모바일 글씨가 여전히 크면 확대를 막는 다른 방법(viewport 설정)을 함께 검토한다
영향 — classic `SurveyForm` 입력창
상태 — active

### Dec-18. 보낸 뒤 창은 그대로, 닫을 때 연 곳으로 돌아감
영향도: significant · 출처: user-suggested

문제 — Dec-16은 "보낸 직후 이전 창으로"로 해석했는데, 사용자 의도는 "피드백 창을 닫을 때 이전 창으로"였다. 보낸 뒤와 닫을 때를 각각 어떻게 할 것인가?
옵션
  (A) 보내면 창을 닫고 이전 창으로 + 성공 토스트 (Dec-16)
  (B) 보내면 창은 그대로 두고 창 안에 감사 안내(토스트 없음). 닫으면(보냈든 안 보냈든, X·바깥·ESC) 연 곳으로: 설정 → 메인, 결과창 → 결과창
선택 — B
근거 — 사용자 정정. 감사 안내가 창 안에 보이니 성공 토스트는 필요 없다. 감사 안내의 "내일 다시 남길 수 있어요"도 빼 달라는 요청(Dec-15와 같은 방향: 하루 1회를 드러내지 않음). 결과창에서 넘어온 사람은 결과창을 보던 중이었으니 닫으면 결과창으로 돌려보낸다. 이 때문에 결과창 작업의 "피드백 창을 닫으면 게임 화면으로"(`result-box.md` 요구사항 3, R-4-2)와 충돌해, 그 문서와 테스트를 함께 고친다
영향 — `useFeedback`(onSent 제거), `FeedbackDialog`·`NewMantleForm`(닫을 때 결과창 다시 열기), `SettingsButton`, `result-box.md` 요구사항 3, `docs/tasks/ui/verification.md` R-4-2, verification F-6, Dec-3, Dec-16
상태 — active
